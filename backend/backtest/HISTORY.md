# Общая история Bybit

`market_history` — отдельный сервис загрузки истории, исходники `cmd/history-sync` и `historysync`. Он хранит 5m OHLCV в существующей `shortlong_backtest.candles`. Расчёт стратегий остаётся в `backtest_worker`, реальные сканеры и alert-engine продолжают использовать свои потоки Redis.

По умолчанию архивируются все **сейчас торгуемые USDT Spot-пары и USDT perpetual Futures Bybit**, с начала дня UTC шесть календарных месяцев назад. У новых инструментов истории до листинга нет. Делистингованные инструменты, которых уже нет в текущем каталоге, автоматически не обнаруживаются; ранее сохранённые свечи не удаляются.

## Управление на локальном компьютере

Из корня репозитория:

```powershell
.\backend\history.ps1 start
.\backend\history.ps1 status
.\backend\history.ps1 audit
.\backend\history.ps1 logs
```

`start` собирает и пересоздаёт API (с миграциями), ClickHouse, загрузчик, backtest worker и frontend. Данные PostgreSQL и ClickHouse остаются в существующих volumes. `status` читает сохранённый прогресс, `audit` проверяет реальные строки и внутренние разрывы в ClickHouse, `logs` показывает ошибки и минутные отчёты. Общий `production.ps1 start/build` также включает новый сервис.

Production: те же сервисы в `compose.yaml`, без `compose.local.yaml`. ClickHouse и служебный HTTP-порт загрузчика не публикуются на хосте. Для чтения статуса:

```sh
docker compose exec -T market_history /app/history-sync -status
docker compose logs --tail 50 -f market_history
```

Настройки окружения Compose:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `MARKET_HISTORY_MARKETS` | `spot,linear` | Рынки каталога |
| `MARKET_HISTORY_MONTHS` | `6` | Глубина первоначальной загрузки, 1–12 календарных месяцев |
| `MARKET_HISTORY_REFRESH_HOURS` | `12` | Интервал массовой дозагрузки новых свечей, 1–24 часа |
| `MARKET_HISTORY_CONCURRENCY` | `32` | Число одновременно обрабатываемых диапазонов, 1–32 |
| `MARKET_HISTORY_RPS` | `30` | Общий лимит REST-запросов модуля истории и бэктеста, 1–30 |
| `BACKTEST_BYBIT_BASE_URL` | `https://api.bybit.com` | Адрес Bybit |

Лимит синхронизирован через Redis и разделяется репликами. У существующих live-сканеров собственные лимиты; при настройке нужно учитывать суммарный трафик с одного IP. Ответ 403 устанавливает общий десятиминутный cooldown для этого модуля. Ошибки транспорта и лимитов не трактуются как отсутствие истории.

## Как загружаются и обновляются свечи

1. Каталог перечитывается при старте и раз в 12 часов вместе с массовой дозагрузкой, с пагинацией для Futures. Ошибки каталога повторяются через 10 минут. Для Futures учитывается `launchTime`; для Spot это поле отсутствует в протоколе.
2. PostgreSQL хранит серию `(market,symbol,5m)`, начальную границу, курсор исторической загрузки и курсор новых свечей. Отсутствующие в обновлённом каталоге инструменты становятся неактивными; данные сохраняются.
3. Новые свечи массово догружаются до фиксированных границ **00:00 и 12:00 UTC** (10:00 и 22:00 Владивостока), с задержкой публикации 10 секунд и проверкой очереди раз в минуту. Перезапуск не сдвигает расписание. Между циклами возраст архива до 12 часов ожидаем. Первоначальная история продолжает загружаться без пауз порциями до 1000 баров, от новых свечей к старым; недогруженные плановые обновления имеют приоритет.
4. Короткий `FOR UPDATE SKIP LOCKED` выдаёт диапазон одной реплике. SQL-транзакция закрывается до HTTP-запросов. Трёхминутная lease и уникальный token защищают прогресс от старого процесса; время обработки ограничено двумя минутами.
5. Общая PostgreSQL advisory lock на серию используется загрузчиком, бэктестом и поиском похожих ситуаций. После получения блокировки перечитывается ClickHouse, скачиваются только отсутствующие диапазоны. Бэктест и поиск по запросу пользователя могут догрузить выбранную монету до последней закрытой свечи, не запуская обход остальных пар. Фоновая индексация похожих ситуаций читает архив без обращений к Bybit.
6. В ClickHouse записываются реальные закрытые свечи. Только после успешной вставки транзакция PostgreSQL передвигает курсор и фиксирует неполные диапазоны. Повтор после обрыва безопасен: `ReplacingMergeTree(version)` и чтение `FINAL` устраняют повторные версии.
7. После простоя сервис продолжает с `live_to`, порциями догружая **весь** пропущенный промежуток. Исторический курсор также сохраняется. Старое обновление «только двух свечей» из backtest worker удалено.
8. Неполные ответы без ошибки сохраняются как доступные строки, а недостающая часть отмечается в `market_history_gaps`. Такие диапазоны перепроверяются раз в сутки. Пустой ответ до листинга не создаёт искусственных свечей; доступность данных и выполнение обхода учитываются отдельно.

Архив накапливается: TTL и автоматического удаления старых свечей нет. Уменьшение глубины не удаляет данные, увеличение ставит более старые диапазоны в работу. После переезда на другой сервер нужно перенести volumes или заново заполнить историю.

## Как понимать status

- `series`: число активных инструментов рынка.
- `historyScanned`: сколько серий полностью обошли первоначальный диапазон.
- `historyBarsToCheck`: сколько 5m интервалов осталось проверить в первоначальной загрузке.
- `historyCheckedPct`: процент **обхода диапазона**, а не гарантированная полнота свечей.
- `maxLiveLagSeconds`: максимальное отставание сохранённого курсора обновления от границы закрытых свечей. При старте фактическая начальная история ещё загружается.
- `refreshHours`, `refreshThrough`, `nextRefreshAt`: интервал и UTC-границы текущего/следующего массового обновления (время в Unix milliseconds).
- `maxScheduledLagSeconds`: отставание от **плановой** границы обновления. Ноль означает, что расписание соблюдено, даже когда `maxLiveLagSeconds` растёт между циклами.
- `errors`: число серий с последней неуспешной попыткой; они повторяются с увеличивающейся задержкой до 10 минут.
- `sourceMissingBars`: число интервалов, по которым источник не вернул свечи при последней проверке диапазона. До следующей проверки значение может отставать от дозагрузки через бэктест. Для Spot сюда может попадать время до листинга; после загрузки нужно сопоставлять с `first_available` и аудитом внутренних разрывов.

`100%` обхода не означает отсутствие разрывов. Для готовности конкретной аналитической задачи проверяйте непрерывность её диапазона через `History.Load` или строгую проверку временных шагов. Особое внимание — новым инструментам, торговым паузам и инструментам с ограниченными торговыми сессиями.

## Подключение других расчётов

```text
Bybit → market_history → ClickHouse 5m
                              ├→ backtest_worker
                              └→ будущий worker поиска похожих ситуаций
```

В Go доступен общий пакет `shortlong/backtest/marketdata`:

- `ClickHouse.Read`: прямое чтение сохранённых свечей с `FINAL`.
- `History.Load`: получение полного ряда с заполнением пропусков. Для 15m/1h/4h используется прежний готовый ряд, если он полон; иначе загружается общий 5m ряд и агрегируется.
- `Aggregate`: open первой свечи, high максимум, low минимум, close последней, volume сумма. Неполное или не выровненное по UTC окно отклоняется.
- `History.SyncRange`: ограниченная порция фоновой архивации, допускает неполную историю; вызывающая сторона обязана учитывать покрытие. Для расчётов, требующих непрерывности, используйте `Load`.

Прямое чтение для воркера на другом языке — параметризованный запрос:

```sql
SELECT time, open, high, low, close, volume
FROM shortlong_backtest.candles FINAL
WHERE market = {market:String}
  AND symbol = {symbol:String}
  AND timeframe = '5m'
  AND time >= {from:Int64}
  AND time < {to:Int64}
ORDER BY time;
```

Время — начало свечи, Unix milliseconds, UTC; диапазон `[from,to)`. На входе аналитики проверяйте шаг ровно 300000 ms и число строк. Не переносите будущие свечи в признаки сравниваемого прошлого участка. У нового аналитического воркера должны быть собственные очередь, задания и результаты; источник свечей общий.

Переносить шестимесячный архив в краткосрочные Redis-потоки live-сканеров не требуется. Таблица сейчас содержит только Bybit; для второй биржи потребуется добавить `exchange` в структуру и ключ, а также в метаданные и блокировки.

## Проверка разработки

Миграция: `backend/api/internal/database/migrations/064_add_market_history.sql`.
Тесты: `historysync/store_test.go`, `marketdata/aggregate_test.go`, `marketdata/history_integration_test.go` и существующий набор модуля.

Для интеграционных тестов используется отдельный `compose.test.yaml`, PostgreSQL `backtest_test`, отдельный ClickHouse и Redis. На тестовой БД нужны таблица users и миграции 063/064. Не указывайте рабочие базы в переменных `BACKTEST_TEST_*`.

Проверяются конкурентный захват, истечение lease, запрет записи старым token, повтор после ошибки, приоритет актуальных свечей, сохранение курсора при обновлении каталога, явное отсутствие данных, корректная агрегация OHLCV и повторное использование 5m без новых REST-запросов.

Источники: [Bybit Kline](https://bybit-exchange.github.io/docs/v5/market/kline), [каталог Bybit](https://bybit-exchange.github.io/docs/v5/market/instrument), [лимиты Bybit](https://bybit-exchange.github.io/docs/v5/rate-limit).
