# Снижение нагрузки ClickHouse — 6 октября 2026

Установлено на `192.168.0.124`, ClickHouse **25.8.33.6**.

## Причина

ClickHouse расходовал примерно три ядра преимущественно на слияния служебных
журналов. `text_log` отдельно записывал уровень Trace, несмотря на Warning
у файлового logger. Профилирование создало около **4,26 млрд строк / 83 ГБ**
в `trace_log`. Четыре merge-потока с коэффициентом 8 допускали 32 фоновых
контекста. Слияния широкого `metric_log` упирались в общий лимит памяти 4 GiB
и повторялись: перед обновлением — **389 записей Error за минуту** от двух
компонентов фонового выполнения. Это внутренний журнал ClickHouse; отсутствие
ошибок в Docker stdout не означало отсутствие этих ошибок.

## Что изменилось

- `clickhouse.xml`: два merge-потока, коэффициент 2, максимум четыре контекста.
  Пороговые настройки свободных контекстов согласованы с новым размером пула.
  Лимиты остались прежними: 3 CPU / 6 GiB контейнеру, 4 GiB ClickHouse.
- `clickhouse-users.xml` и новый read-only mount в `compose.server.yaml`:
  отключены временное/CPU/память профилирование запросов и processor profiles;
  глобальный memory profiler также отключён.
- Отключены новые записи `trace_log`, `processors_profile_log`,
  `query_metric_log`, `asynchronous_metric_log`. Текущие `system.metrics`,
  `system.asynchronous_metrics`, мониторинг приложения и Telegram-бот работают.
- Новый `text_log`: Warning/Error, сброс раз в 30 секунд; `metric_log`:
  измерение раз в 15 секунд, сброс раз в минуту. Обоим — дневные партиции,
  TTL 3 дня и блоки слияния 1024 строки. `query_log`/`part_log`: TTL 7 дней,
  дневные партиции, сброс раз в 30 секунд. Истёкшие партиции удаляются целиком,
  асинхронно; срок считается по UTC-дате, не точно до секунды.
- `clickhouse-log-archive.py`: сохранение восьми старых журналов через
  переименование и `DETACH TABLE … PERMANENTLY`, с manifest для восстановления.
  Только явный список служебных таблиц; включённый log writer блокирует запуск.
  Скрипт поддерживает повторный запуск незавершённой миграции. Таблицы свечей
  не входят в разрешённый список. Файлы и таблицы не удаляются.
- Добавлены unit-тесты защиты скрипта и отдельный Docker integration test;
  Python-кеш исключён из Git.

Старые журналы — **4 701 791 604 физических строки / 89 436 467 569 байт** —
остались на HDD, но больше не участвуют в фоновых слияниях. Это снятие нагрузки,
а не освобождение диска или резервная копия на отдельном носителе.

## Измерения

Два 20-секундных замера штатно работающего сервера; временный QA-контейнер
и браузерный тест завершились перед вторым замером. Docker CPU 100% означает
одно логическое ядро; в сервере восемь логических ядер.

| Показатель | До | После |
|---|---:|---:|
| Общая занятость CPU, среднее | 62,17% | 34,08% |
| Температура CPU Package, среднее | 62,6°C | 42,2°C |
| ClickHouse, Docker CPU, отдельный снимок | 312,34% | 3,83% |
| ClickHouse, доля всех 8 потоков | 39,04% | 0,48% |
| CPU PSI `some avg10` | 37,02% | 7,52% |
| Error в text_log за последнюю минуту | 389 | 0 |

Аппаратного троттлинга нет. Замер показывает устранение постоянной нагрузки
от журналов; при следующем архивном пакете, бэктестах или активном рынке
CPU и температура могут снова подняться. Сокращение пула меняет параллелизм
фоновых слияний; длительность будущих больших пакетов этим замером не измерена.
Частота сканирования, число бирж и настройки загрузки свечей не снижались.

## Отчёты и восстановление старых журналов

На сервере в `/opt/shortlong/reports`:

- `clickhouse-budget-before-20261006.json`, `clickhouse-budget-after-20261006.json`;
- `clickhouse-budget-comparison-20261006.json`, `clickhouse-budget-verification-20261006.json`;
- `archive-clickhouse-budget-status-20261006.json`;
- `clickhouse-log-archive-20261006_131449.json`: имена, исходный DDL, части,
  пути метаданных и статус каждого сохранённого журнала;
- `clickhouse-budget-backup-20261006_131449/`: исходные конфигурации,
  DDL/UUID свечей и контрольные данные до/после.

Чтобы прочитать старый журнал, подключить **архивное имя** из manifest,
остановить его слияния и после исследования снова отключить. Например,
в авторизованном `clickhouse-client`:

```sql
ATTACH TABLE system.archived_text_log_20261006_131449;
SYSTEM STOP MERGES system.archived_text_log_20261006_131449;
-- Запросы к сохранённому журналу.
DETACH TABLE system.archived_text_log_20261006_131449 PERMANENTLY;
```

Новые `system.text_log`/`metric_log` независимы от старых архивных таблиц.
Повторять миграцию при обычном деплое не нужно. Для миграции старой установки
сначала временно отключить все восемь writers через `remove="1"` и перезапустить
ClickHouse, затем запустить архивирование с уникальным suffix/manifest,
вернуть штатную конфигурацию и перезапустить ClickHouse. Не восстанавливать
старые таблицы под текущими именами при работающих writers.

Основание настроек: официальная документация
[ClickHouse system logs](https://clickhouse.com/docs/reference/settings/server-settings/settings/other),
[memory profiler](https://clickhouse.com/docs/reference/settings/server-settings/settings/total-memory).
Совместимость проверена непосредственно на используемой версии 25.8.33.6.
